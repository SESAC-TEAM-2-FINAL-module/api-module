### 0.1 배경 (짧게)

v1.5 7.4절의 적조 위험도 지수(수온·적조 속보·염분·클로로필의 가중 합산)를 이 모듈 범위에 넣었다(개정 20). 판정·값은 모듈이 만들고 대시보드는 표시만 한다. **가중치·점수·구간·단계 경계·클로로필 상승 규칙의 값은 정해지지 않았다** — 판정 정의에 `<미결>`로만 두고, 미결이면 4.10절 ①~④ 규칙(`RULE_UNDECIDED`)으로 돈다. 검사는 테스트 안에서만 주는 **시험용 판정 정의**로 짠다.

### 0.2 지키는 것

- `<미결>` 값을 채우지 않는다 — `config/definitions.yaml`·`ci/gate/expected.yaml`에 키만 `<미결>`로 둔다(같은 작업에서 두 파일을 함께 고친다 — 게이트 금지 규칙). v1.5 원안 값(가중치 0.40·0.30·0.15·0.15 등)을 기본값으로 넣지 않는다. 시험용 값은 테스트 코드 안에만 둔다
- 운영 DB·외부 DB에 접속하지 않는다. DB 검사는 테스트 컨테이너로만. `.env` 값을 출력하지 않는다. 키 검사는 `python ci/scan_keys.py`로만
- 테이블 정의 변경은 **정의 제안**(`tables.py`·DDL 생성본)의 변경이다. 마이그레이션을 만들지 않는다
- DB `ENUM`·`JSONB` 연산자·배열 타입 금지 — 코드 값은 `VARCHAR` + `CHECK`. 방언 분기는 `dialect.py`에만
- 단계 전용 코드끼리 가져다 쓰지 않는다 — grading과 evaluation이 함께 쓸 것이 생기면 `common/`으로
- `derivation = COMPUTED`인 지수 행의 `alertable`은 언제나 `false`. `provenance = NONE`이어도 계산할 수 있었던 값은 저장한다
- 계약 `queue-v1`은 바꾸지 않는다(`grade.done.axis`는 문자열). 매니페스트(`handoff/k8s/`)·대시보드 인계 묶음(`handoff/dashboard-deliver/`)은 고치지 않는다 — 대시보드 전달은 구현 뒤 사용자가 정한다
- 설명 문장(코드 주석·`HANDOFF.md`·계약 문서)의 근거는 **계획서 4.10절 문장을 옮긴다** — 다르게 풀어 쓰지 않는다
- 파일 줄바꿈: 이 저장소는 `core.autocrlf=true`다. 새로 만드는 생성본(DDL)은 기존 생성기 방식 그대로 두고, 바이트를 비교하는 검사는 줄바꿈을 LF로 맞춰 비교한다

## 1. 작업

경로는 `src/api_module/` 기준.

1. **테이블 모델 — `common/repository/tables.py`**
   - `AXIS_VALS`에 `red_tide_risk` 추가(축 `CHECK` 4곳이 함께 바뀐다)
   - 새 표 `risk_index_factors`(PK `farm_id`·`factor`), `risk_index_levels`(PK `farm_id`) — 열·NULL 여부·`CHECK`는 계획서 5.3절과 `repository` skill ③-3 그대로. `factor` `CHECK` = 4개 이름, `excluded_reason` `CHECK` = `NO_INPUT`·`INPUT_NONE`·`SENSOR_QUALITY`·`RULE_UNDECIDED`. 단계 코드 `CHECK`는 넣지 않는다(코드 이름 미결)
   - 두 표는 **결과 테이블**이다 — `OPTIONAL_TABLES`에 넣지 않는다(기동 시 검사가 요구)
   - DDL 생성본 두 벌(`contracts/tables/schema_pg.sql`·`schema_my.sql`)을 기존 생성기로 다시 만든다
2. **DB 접근 — `common/repository/base.py`·`sql.py`**: 두 표의 upsert(키 = PK), 양식장 단위 삭제(4.10절 ①·④에서 기존 행을 지운다), 지수 입력 읽기(양식장의 4개 입력 축 `farm_readings` 현재값), OK 조건 3의 원천 행 `flags` 조회(클로로필 `survey_observations` — 정점·`observed_at_utc`·표층·클로로필 / 염분 `observations` — 관측소·`observed_at_utc`·염분). **한 트랜잭션** 안에서 쓸 수 있게 기존 `transaction()` 방식을 따른다
3. **판정 정의 — `config/definitions.yaml`·`ci/gate/expected.yaml`**: 계획서 7.7 ① YAML의 `risk_index.*` 10개 키를 `<미결>`로, `contracts.tables`를 `tables-v3`로. `contracts/release/image_notice.json` 예시의 `tables-v2`도 `tables-v3`로. 게이트(`--warn-pending`)가 새 `<미결>`을 경고로 보이는지 확인
4. **지수 계산 — `grading/`** (계산은 순수 함수 모듈로 분리, 예: `grading/_risk_index.py`)
   - 4.10절 그대로: 항목 4개의 점수·점수 범위(구간 `[min, max)`, 입력 `lower`~`upper` 위의 최솟값·최댓값), OK 조건 1~4와 `excluded_reason` 판정 순서, 기여도·`value`·`lower`·`upper`(제외 항목 가중치를 `upper`에 더함 — 재정규화하지 않음), `provenance`(OK 수 ≥ `min_factors_ok` → `INTERPOLATED`, 미만 → `NONE`·`INSUFFICIENT_FACTORS`), 단계(`min ≤ x`인 것 중 `min`이 가장 큰 코드, `level_straddle = (level_at_lower ≠ level_at_upper)`), `observed_at_utc` = OK 입력 중 가장 이른 값
   - **`nearby_bulletin`은 `value`(밀도)를 보지 않는다** — `grade`가 있거나 유효 기간 안 속보 없음이면 OK(4.10절 OK 조건 1)
   - **`<미결>` 처리 ①~④**와 `none_reason` 우선순위(`INVALID_COORDS` > `RULE_UNDECIDED` > `INSUFFICIENT_FACTORS`), 좌표 불량 양식장은 양식장 좌표 검증 결과로 판단
   - 지수 행 고정값: `derivation = COMPUTED`, `alertable = false`, `source_ref`·`validated_scope`·`grade`·`unit`·`distance_km` = `NULL`
   - **연결**: `obs.loaded`·`interp.done` 처리에서 입력 축(`red_tide`·`water_temp`·`salinity`·`chlorophyll`) 행을 쓴 양식장마다 지수를 다시 계산. 입력 축 행·지수 세 표·두 축의 `farm_reading_history`를 **한 트랜잭션**에, 커밋 뒤 축 `red_tide_risk`의 `grade.done` 한 건(계약 `queue-v1` 형식 — `axis: "red_tide_risk"`). 지금 readings와 history를 따로 커밋한다면 하나로 묶는다. 입력 읽기는 그 트랜잭션 안의 현재값이다
   - **기동 시 검사**(K9): 값이 정해진 키만 — 점수 ∈ [0, 1], Σ`weight` = 1(허용 오차 1e-9), `levels`의 첫 `min` ≤ 0. 어기면 멈추고 위반을 보고. `<미결>` 키는 검사하지 않는다
5. **축 상태 — `evaluation/`**: 축 `red_tide_risk`는 **`AXIS_ADAPTER`에 넣지 않는다**(수집 원천 대응이 없다). `grade.done`(`axis = red_tide_risk`)을 받으면 `provenance = NONE` → `NOT_USABLE`(`reason` = `none_reason`), 그 밖 → `NORMAL`. sweep은 이 축에서 **산출 지연(`GRADING_STALE`)만** 본다 — 4.9절 기준 그대로(정기 경로 적재 뒤 이 축의 `farm_readings`가 한계 안에 갱신되지 않음). 커버리지·계절·3번 묶음·신선도 판정을 적용하지 않는다. `basis_utc` 쓰기 규칙(4.9절)은 다른 축과 같다
6. **계약 문서 — `contracts/tables/dashboard_contract.md`**: 계약 버전 줄을 `tables-v3`(개정 20 — 위험도 지수)로, 필드 의미 표에 계획서 5.5절의 새 두 행과 `lower`·`upper` 정의를 그대로. 새 표 두 개의 열 설명은 계획서 4.10·5.3절에서 옮긴다
7. **`handoff/HANDOFF.md`** (인계 전 초기본) — "추가 요청 — 적조 위험도 지수 (개정 20)" 절: 새 표 2개(DDL 생성본 위치), 축 목록 `CHECK` 4곳에 `red_tide_risk` 추가(열 변경 없음), `none_reason` 새 값, 계약 `tables-v3`, 적용 순서(DDL 적용 → 새 이미지 — 기동 시 테이블 검사가 새 표를 요구한다)

## 3. 순서 · 중단 조건

- 순서 1 → 8. 테스트는 각 작업과 함께 써도 된다
- 계획서 4.10절·5.3절과 skill·코드가 다르게 읽히는 곳, 4.10절이 정하지 않은 동작이 필요한 곳을 만나면 **멈추고 보고한다**(고르지 않는다)
- 기존 테스트가 이 변경으로 깨지는데 그 테스트를 약하게 해야만 통과한다면 멈추고 보고한다. 기존 테스트의 기대값이 **축 목록·표 목록이 늘어난 것만으로** 바뀌는 경우(예: 표 개수, 축 목록 비교)는 고쳐도 되고 보고서에 적는다
- grading의 트랜잭션 구조를 바꾸다 기존 동작(입력 축 행·history·`grade.done`)이 달라지면 멈추고 보고한다
