### 0.1 배경 (짧게)

운영에서 `areas`·`axis_coverage`를 DB에 넣는 곳이 없었다(`load_seeds`는 테스트에서만 호출). 그래서 grading의 적조 대응(`grading/main.py` `get_areas`)이 늘 0건, evaluation의 `farm_areas`·커버리지·계절 판정(`evaluation/main.py` `get_areas`·`get_axis_coverage`)이 조용히 비었다. 사용자 결정(2026-10-02): 운영 적용은 **DB 소유 측**이 모듈이 넘긴 SQL 생성본으로 하고, 모듈은 운영 DB에 시드를 쓰지 않는다. 시드는 모두의 협의 아래 파일을 고쳐 나눠 가진다.

### 0.2 지키는 것

- 운영 DB·외부 DB에 접속하지 않는다. DB 검사는 **테스트 컨테이너**(기존 `tests/db/` 방식)로만 한다
- `.env`의 값을 읽어 출력하지 않는다. 키 검사는 `python ci/scan_keys.py`로만, 결과는 건수만
- 방언 분기는 `common/repository/dialect.py` 밖에 쓰지 않는다
- 단계 전용 코드(`collector/`·`processor/`·`interpolation/`·`grading/`·`evaluation/`)끼리 가져다 쓰지 않는다 — 공유는 `common/`
- 시드 파일(`seeds/*.yaml`)의 **내용**을 바꾸지 않는다
- 테이블 정의(`tables.py`·DDL 생성본)를 바꾸지 않는다 — 이 작업에 스키마 변경은 없다

## 1. 작업

경로는 `src/api_module/` 기준.

1. **시드 읽기를 `common/seeds.py`로** — `processor/adapters/bulletin/_seed.py`의 `_read_seed`와 `_adapter.py`의 `_load_area_aliases` 파일 읽기를 하나로 모은다. 기존 동작 유지: 파일 없음·빔·항목 형식 오류면 `RuntimeError`(점검 C11). 시드 경로는 지금과 같은 위치(저장소 루트 `seeds/`, 이미지에서도 같은 상대 위치)를 찾는다. `load_seeds`·`_load_area_aliases`는 이 함수를 부른다. 파일 이름은 계획서 6.1절 *(위치는 제안)* — 다르게 두면 보고서에 적는다
2. **시드 적용 SQL 생성 — `common/repository/dialect.py`** — `generate_seed_sql_pg()`·`generate_seed_sql_my()`(기존 `generate_ddl_*`와 같은 모양, `common/repository/__init__.py`에서 내보냄). 출력 규칙(4.3절 "넘기는 것"):
   - 머리 주석: 생성 안내, 세 시드 파일 각각의 SHA-256
   - 한 트랜잭션: PG `BEGIN; … COMMIT;`, MySQL `START TRANSACTION; … COMMIT;`. 세 표를 `DELETE FROM`으로 비운 뒤(**`TRUNCATE` 금지** — MySQL 암묵 커밋) 시드 행 전체 `INSERT`
   - 행 순서는 PK 순(결정적 출력 — 같은 시드면 바이트가 같다)
   - 문자열은 방언에 맞게 이스케이프, 실수는 왕복 가능한 표기(`repr`), 불리언·NULL은 방언 표기, `season_months`(JSON 열)는 JSON 문자열 리터럴
   - 생성본을 `contracts/tables/seeds_pg.sql`·`seeds_my.sql`로 쓴다(DDL 생성본과 같은 폴더)
3. **빈 시드 기동 검사 — `common/contract_check/`** — 함수 하나(예: `check_seed_tables(repo, tables)`): 주어진 표 중 0행인 것이 있으면 `SystemExit`으로 멈추고 표 이름을 보고. 행 수 조회는 repository 읽기 메서드로(필요하면 `base.py`·`sql.py`에 추가)
   - `grading/main.py`: `check_schema()` 다음에 `areas`
   - `evaluation/main.py`: `_repository()`(`evaluate`·`sweep`이 쓴다)에서 `check_schema()` 다음에 `areas`·`axis_coverage`. **`gate`에는 걸지 않는다**(DB 없이 돈다 — 지금도 `_repository()`를 부르지 않는지 확인)
   - processor·interpolation·collector에는 넣지 않는다
4. **서비스 전 점검 `seed-check` — `processor/main.py`** — 하위 명령 `seed-check`. **`_m.startup()`을 타지 않는다**(운영 조정을 읽지 않고 `ops_events`에 쓰지 않는다). `DATABASE_URL`로 엔진 → `check_schema()` → 대조 → 차이 표를 표준 출력에 → 차이가 있으면 종료 코드 1, 없으면 0. **DB에 쓰지 않는다**. 대조 항목(4.3절 "서비스 전 점검"):
   - ① DB 세 표 = 이미지 시드 파일 — 빠진 행·더 있는 행·값이 다른 행(키 기준). `season_months`는 해석한 값으로, 실수는 같은 값으로 비교
   - ② `area_aliases.area_id`·`axis_coverage.area_id` ⊂ `areas.area_id`
   - ③ 적조 현재값 유효 기간(판정 정의 `bulletin.current_window_days`, KST 날짜 기준 — grading 적조 유효 기간과 같은 기준) 안 속보의 `bulletin_detail_areas.area_id`(NULL 제외) ⊂ `areas.area_id`. 조회 메서드는 `common/repository/`에
   - 대조 로직은 `common/`에 둔다(processor는 명령 연결만) — 테스트가 함수로 부를 수 있게
5. **`handoff/HANDOFF.md`** (인계 전 초기본) — "추가 요청 — 해역 시드 운영 적재 (개정 19)" 절: 생성본 두 벌의 위치와 적용 방법(DB 소유 측), 변경 조항(모두의 협의 아래 파일을 고쳐 나눠 가진다), 반영 순서(추가·변경: DB → processor 롤아웃 / 삭제: processor 롤아웃 → DB), `seed-check` 명령과 필요한 환경(`DATABASE_URL`만), **배포 선행 조건**(DDL 적용 → 시드 적용 → `seed-check` 통과 → `grading`·`evaluation` 배포 — 빈 시드면 두 이미지는 기동하지 않는다). 7절 "기동 시 검사 항목"에 빈 시드 검사 추가. 매니페스트(`handoff/k8s/`)는 고치지 않는다
6. **테스트** — 아래 2절. 기존 테스트가 빈 시드 DB로 grading·evaluation을 기동하고 있다면 시드를 넣도록 고친다(검사를 약하게 하지 않는다)

| SD1 | 빈 시드 기동 검사 (DB) | `areas` 0행 DB에서 grading 기동이 멈춘다. `areas` 0행 또는 `axis_coverage` 0행 DB에서 evaluation `evaluate`·`sweep`이 멈춘다. `gate`는 그대로 돈다. processor는 빈 시드 DB에서도 기동한다. 시드를 넣으면 셋 다 기동한다 |
